## 2. Expanded Research on Production Readiness

While `conxian-gateway` and `conxian-nexus` maintain a clean CI baseline and full build compliance (version `v0.1.5`, Rust `1.98.1`), moving from a CI-green, fail-closed state to full production deployment requires resolving six critical cryptographic and attestation gates.

```
+-----------------------------------------------------------------------------------+
|                            PRODUCTION READINESS GATES                             |
+-----------------------------------------------------------------------------------+
| 1. BitVM2/BitVM3 Verification Surface  --> Fail-closed -> GC/Groth16 Verifier   |
| 2. Enclave Remote Attestation Evidence --> AWS Nitro / Android StrongBox TEE      |
| 3. Liquid / Elements SPV Proof Wiring  --> Fail-closed -> Elements SPV Verification|
| 4. Curve / Verifier Ownership Contract  --> Gateway BN254 ↔ Nexus BLS12-381      |
| 5. DLC Bond & Oracle Execution Engine  --> Schnorr Attestation + CET Construction |
| 6. sBTC Peg & RGB Transition Depth     --> L1 Header Proof + Stash Ownership      |
+-----------------------------------------------------------------------------------+
```

### 2.1 Cryptographic Verifier Surface & Curve Ownership (G-2 / #189 / Nexus #169)
- **Problem Statement**: Gateway exposes a backend-neutral BN254 Groth16 envelope, whereas `conxian-nexus` historically called `ark_groth16::Groth16::<Bls12_381>::verify(...)` with caller-supplied verification keys (VKs). Direct wiring without a unified ownership contract risks security impedance mismatch.
- **Production Requirement**:
  1. Define a single canonical curve and verifier ownership specification binding `circuit_id`, `vk_hash`, `public_inputs_hash`, and `state_root`.
  2. Implement BN254 pairing verifier support within `conxian-nexus` to accept Groth16 proofs generated by client-side ZK-circuits.
  3. Ensure all verification failures default strictly to fail-closed behavior (`Err(VerificationError::InvalidProof)`), avoiding mock success paths in value-bearing flows.

### 2.2 BitVM2 & BitVM3 Garbled-Circuit Fraud Proofs (R32 / R40)
- **Status**: Research / Fail-Closed (Gated by Gateway #189 and Nexus #169).
- **Production Requirement**:
  1. **BitVM2 Job Card Settlement (R32)**: Gate `/v1/job-card/settle` persistence on cryptographic proof validation using a reviewed Groth16 / BN254 verifier.
  2. **BitVM3 Garbled Circuits (R40)**: Keep BitVM3 adapter fail-closed until a audited, sub-200,000 cycle garbled-circuit / recursive proof folding verifier is wired.
  3. **Challenge-Response Window**: Standardize optimistic challenge windows (e.g., 1,008 Bitcoin blocks) with automatic slashed collateral distribution handled via non-custodial DLC/Taproot contracts.

### 2.3 Enclave Remote Attestation & TEE Evidence (Enclave SDK P0 Gates)
- **Status**: Gated on `enclave-sdk` issues #202, #240, #241, #242.
- **Production Requirement**:
  1. **AWS Nitro Enclaves & Android StrongBox**: Integrate hardware-root-of-trust remote attestation (Nitro COSE sign1 certificates & StrongBox key attestation) into the trust policy engine (`x-conxian-trust-metadata`).
  2. **Nonce & Replay Protection**: Require fresh attestation quotes for every sovereign settlement session with maximum 300-second freshness windows.
  3. **Key Isolation**: Enforce zero-custody key management where signing keys never exit TEE memory unencrypted.

### 2.4 Liquid / Elements SPV & Confidential Proof Wiring
- **Status**: Fail-Closed (Elements proof backend unwired).
- **Production Requirement**:
  1. Replace fail-closed stub in `LiquidAdapter` with full Elements block header traversal, SPV transaction inclusion proof verification, and Confidential Assets range proof validation.
  2. Implement peg-in / peg-out validation connecting Liquid L2 block commitments back to Bitcoin L1 parent block headers.

### 2.5 DLC Bond Lifecycle & Oracle Attestation Engine (Candidate G-DL2 / Candidate N)
- **Status**: Active Engine (`DlcExecutionEngine` in `dlc_oracle.rs`).
- **Production Requirement**:
  1. Validate $k$-of-$n$ threshold Schnorr signatures over outcome digests before executing Contract Execution Transactions (CETs).
  2. Enforce timelocked Refund Transaction (`DlcRefundTx`) availability for deterministic party recovery during oracle stall or network partition events.

## 3. Nexus Business Opportunities & External Decentralized System Integration

Conxian Nexus acts as the protocol coordination engine connecting Gateway settlement instances to global decentralized networks. By integrating with leading L1/L2 and DLT protocols, Nexus creates multi-rail arbitrage, liquidity routing, and cross-chain compliance opportunities.

```
+-----------------------------------------------------------------------------------+
|                        NEXUS DECENTRALIZED PARTNER RAIL MATRIX                    |
+-----------------------------------------------------------------------------------+
| Decentralized System  | Ingress Vector             | Nexus Business / Monetization Opportunity |
+-----------------------+----------------------------+--------------------------------------+
| Canton Network & CCIP | RWA Daml ACS State & CCIP  | Institutional RWA Cross-Chain Clearing|
| peaq DLT & DePIN      | Machine DIDs (DIMO/Helium) | Machine-to-Machine Micro-Settlements  |
| ISO 20022 / BRICS DLT | pacs.008 / mBridge CBDC    | Sovereign Cross-Border ERP Settlement |
| Stacks / sBTC         | L1 Bitcoin Anchors / sBTC  | Bitcoin DeFi & Yield Indexing         |
| Babylon Protocol      | EOTS Staking & Sashing     | BTC Shared Security & Attestation     |
| Fedimint              | Blind-Signature Notes      | Private Community Banking & Settlement|
+-----------------------------------------------------------------------------------+
```

### 3.1 Canton Network & Chainlink CCIP (Candidates I, J, S)
- **Opportunity**: Canton Network powers $6T+ in tokenized Real-World Assets (RWAs) across institutional banking.
- **Nexus Role**:
  - **CBTC Reserve Verification (Candidate I)**: Verify non-custodial $k$-of-$n$ Schnorr attestations and L1 UTXO reserve proofs without holding private keys.
  - **Daml ACS State Translation (Candidate J)**: Translate Daml Active Contract Set states into Bitcoin Universal Contract References (UCR).
  - **CCIP Cross-Chain Routing (Candidate S)**: Provide authenticated cross-chain settlement routing with dynamic risk scoring across EVM and Bitcoin rails.

### 3.2 peaq DLT & DePIN Machine Economy (Candidate R)
- **Opportunity**: Millions of autonomous machine agents (EV charging stations, solar grids, telecom cells, drone fleets) require verifiable identity and instant micropayments.
- **Nexus Role**:
  - **Machine DID Resolution**: Multi-provider DID lookup across peaq DLT, DIMO, Helium, and IoTeX (`resolve_machine_identity`).
  - **RWA Telemetry Verification**: Epoch-based sensor revenue verification and cryptographic proof generation.
  - **M2M Micro-Settlements**: Sub-cent settlement over Lightning and HTTP 402 (X402) rails.

### 3.3 ISO 20022 & BRICS mBridge CBDC (Candidates P & T)
- **Opportunity**: Global central banks and multinational enterprises migrating to ISO 20022 XML (`pacs.008`, `camt.053`) and BRICS mBridge multi-CBDC DLTs.
- **Nexus Role**:
  - **mBridge DLT Attestation**: HotStuff consensus proof verification and secp256k1 threshold signature validation.
  - **Real-Time ERP Treasury Reporting**: Conversion of settlement events into `camt.053` bank statements with OData v4 synchronization for SAP S/4HANA and Oracle Financials Cloud.

### 3.4 Bitcoin L1, Stacks sBTC, Babylon & Fedimint
- **Stacks / sBTC**: Independent L1 Bitcoin verification via raw transaction double-SHA256 hashing, 80-byte header PoW validation, and Merkle inclusion proofs.
- **Babylon Protocol**: Dual-staking security and Extractable One-Time Signature (EOTS) slashability verification for BTC-backed validation.
- **Fedimint**: Blind-signature note verification against guardian quorums for privacy-preserving community settlements.

## 4. Decentralized System Issue Management & Problem Management Strategy

When operating across multiple external decentralized networks (e.g., Canton RPC lag, Stacks congestion, Lightning route failures, BitVM challenge delays), system resilience depends on a structured, automated problem management lifecycle.

### 4.1 Cross-System Issue Handling & Fallback Architecture

```
                    +------------------------------------+
                    |  Inbound Settlement Request        |
                    +------------------------------------+
                                      |
                                      v
                      +--------------------------------+
                      |   Primary Protocol Rail Check  |
                      +--------------------------------+
                                      |
                       [Is Rail Healthy & Verified?]
                                /           \
                             (Yes)          (No: Fault / Lag / Unreachable)
                              /               \
                             v                 v
                 +-------------------+  +------------------------------------+
                 | Execute Primary   |  | Fallback Routing Engine            |
                 | Settlement Path   |  | 1. Downgrade to L1 BTC / Lightning |
                 +-------------------+  | 2. Queue in Atomic Outbox          |
                                        | 3. Emit Telemetry & GitHub Issue   |
                                        +------------------------------------+
```

1. **Automated Degradation & Fallback**:
   - If an external decentralized protocol fails (e.g., Canton node timeout, mBridge signature threshold missed), Gateway statelessly routes the transaction to a secondary rail (e.g., Lightning / sBTC) or queues it in the persistent atomic outbox.
2. **Deterministic Error Handling**:
   - Errors are classified into `TransientNetworkError` (retry with exponential backoff), `CryptographicProofError` (fail-closed, reject request), and `ProtocolVersionMismatch` (flag for automated triage).

## 5. Managing Readiness & Issues via GitHub Issues, Projects, and KB

To maintain operational clarity across `conxian-gateway`, `conxian-nexus`, `conxian-core`, `enclave-sdk`, and `@conxian/client-sdk`, all technical gaps, readiness gates, and external network issues are tracked using standardized GitHub workflows and Knowledge Base assets.

### 5.1 GitHub Issue Lifecycle & Templates
1. **Issue Classification**:
   - `repo_baseline_improvement.yml`: Used for baseline code, hygiene, CI/CD, and policy improvements.
   - `bug_report.yml`: Used for unexpected runtime failures, cryptographic rejection errors, or API contract drifts.
   - `governance_request.yml`: Used for CXIP proposals, partner rail additions, or version promotion reviews.
   - `cxn_bounty_job_card.yml`: Used for open community or partner bug bounties and research grants.
2. **Mandatory Issue Metadata**:
   - **Labels**: `gate:p0`, `gate:p1`, `rail:canton`, `rail:peaq`, `rail:bitvm`, `type:readiness`, `type:security`.
   - **Cross-Repo References**: Linking issues across repositories (e.g., Gateway #189 ↔ Nexus #169 ↔ Enclave #202) to ensure synchronized resolution.
